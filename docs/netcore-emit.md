# Эмит netcore: что порождается

Режим включается ключом `serverEmitKind: "netcore"`. Реализация — `bin/nsgGenNetcore.dart`
(около 3000 строк). Результат — **самостоятельный сервер ASP.NET Core**, не зависящий от
`NsgServerClasses` и windows-приложения метаданных: PostgreSQL через EF Core, обмен по прежнему
wire-формату `nsg_data`.

## Состав вывода

Каталог задаётся ключом `netcoreOutputPath`.

| каталог / файл | что внутри |
|---|---|
| `Models/<Type>.cs` | сущности EF Core по описанию типа |
| `Configurations/<Type>Configuration.cs` | отображение сущности на таблицу и колонки (`pgTableName`, `pgColumnName`) |
| `Configurations/<Type>FieldMap.cs` | соответствие «поле обмена ↔ свойство C#»; wire-имя это `databaseName`, а не имя колонки |
| `Configurations/NsgTypeNameMap.cs` | соответствие имён типов обмена типам C# |
| `Configurations/NsgTypeFieldMapRegistry.cs` | реестр `FieldMap` по runtime-типу — нужен сериализатору |
| `Configurations/NsgGeneratedServicesExtensions.cs` | регистрация служб в контейнере |
| `Configurations/NsgDatabaseMigrator.cs` | сверка версии схемы при запуске и применение миграций (см. ниже) |
| `Controllers/<Type>Controller.cs` | порождаемый контроллер (перезаписывается) |
| `Controllers/<Type>Controller.Custom.cs` | заготовка для своей логики (**не перезаписывается**) |
| `Wire/…` | трансляция запросов и сериализация (см. [wire-and-schema.md](wire-and-schema.md)) |
| `Auth/…` | JWT: `NsgLoginDto`, `NsgJwtOptions`, `IJwtTokenService`, `JwtTokenService`, обработчик сырого токена |
| `AppDbContext.Designer.cs` · `AppDbContext.cs` | контекст: порождаемая часть и ручная |
| `<Namespace>.csproj`, `Program.cs`, `appsettings.json`, `launchSettings.json` | размещение приложения |
| `<Namespace>.Tests/` | заготовка тестового проекта: smoke и round-trip обмена |
| `Enums/…` | перечисления |

## Что перезаписывается, а что нет

Разделение проведено намеренно и опирается на `_writeOneShot`: файл пишется, **только если его ещё
нет** (либо при `forceOverwrite`).

**Перезаписывается при каждой генерации:** модели, конфигурации, `FieldMap`, реестры, порождаемая
часть контроллера, wire-слой, `AppDbContext.Designer.cs`, `NsgDatabaseMigrator.cs`.

**Пишется один раз и далее не трогается:** `*.Controller.Custom.cs`, ручная часть `AppDbContext.cs`,
`csproj`, `Program.cs`, `appsettings.json`, `launchSettings.json`, файлы тестового проекта, файлы
аутентификации.

Практическое следствие: **своя логика живёт в `.Custom.cs`**, и перегенерация её не затирает. Правка
порождаемого файла будет потеряна при следующем запуске.

## Порождаемые операции контроллера

Состав определяется флагами метода (`allowGetter`, `allowCreate`, `allowPost`, `allowDelete` —
см. [config-reference.md](config-reference.md)).

| операция | маршрут | поведение |
|---|---|---|
| чтение | `POST Api/<Type>` | тело — параметры запроса `nsg_data`: фильтр `NsgCompare`, сортировка, `ReadReferences`, `Top` |
| запись | `POST Api/<Type>/Post` | принимает **массив** объектов; для каждого — поиск по первичному ключу: найден → обновление, не найден → вставка |
| удаление | `POST Api/<Type>/Delete` | массив идентификаторов |

Точки расширения в `.Custom.cs`: `CustomizeReadQuery`, `OnBeforeSave`, `OnBeforeDelete`.

### Режим записи

По умолчанию `Post` выполняет upsert: найденный по идентификатору объект обновляется присланным
содержимым. Для типов, которые пишутся один раз и не изменяются, задаётся `postMode: "insert-only"`
(см. [config-reference.md](config-reference.md)): совпадающее содержимое принимается как повтор,
отличающееся отклоняется с `409`.

Сравнение выполняет порождаемый `Wire/NsgWireComparer.cs` — по объектам обмена, а не по сущностям.
Перед отказом вызывается частичный метод `OnPostConflict(incoming, existing)`, в котором проект может
записать расхождение в свой журнал; заготовка объявлена в `.Custom.cs`.

## Вход по одноразовому коду

Включается ключом `anonymousCodeAuth: true`. Предназначен сценариям, где у участника нет и не должно
быть учётной записи: опросы, тестирования, учебные работы с анонимной моделью данных.

Код выдаётся сервером при подключении и служит **единственным** ключом доступа к собственным данным.
Порождаются четыре составляющие:

| файл | назначение |
|---|---|
| `Auth/NsgAccessCode.cs` | выдача кода, хеширование, сверка за постоянное время |
| `Auth/NsgCodeAuthOptions.cs` | длина кода, общий секрет, предел попыток обмена |
| `Auth/INsgCodeIdentityStore.cs` | **точка расширения проекта**: как хранятся коды и что считается участником |
| `Controllers/NsgCodeAuthController.cs` | `Issue` — выдать код новому участнику, `Exchange` — обменять код на токен |

Заложенные решения и их причины:

* **Код случаен и длинен.** Алфавит из 32 знаков без визуально неразличимых (`0/O`, `1/I/L`), по
  умолчанию 10 знаков — ровно 50 бит энтропии. Длина короче 8 знаков отклоняется: меньше 40 бит
  подбирается.
* **Хранится хеш, а не код.** Утечка хранилища не открывает доступ к данным. Соль на запись
  невозможна — поиск идёт по хешу; её отсутствие безопасно именно потому, что код случаен: словарной
  атаки, от которой защищает соль, здесь не существует. Общий секрет (`Pepper`) задаётся конфигурацией
  развёртывания.
* **Сверка за постоянное время** (`FixedTimeEquals`): время ответа не должно зависеть от числа
  совпавших знаков.
* **Ответ на неизвестный код неотличим от ответа на ошибочный.** Иначе по различию ответов можно было
  бы отделять существующие коды от несуществующих.
* **Ограничение частоты обмена** регистрируется автоматически (`nsg-code-exchange`, по умолчанию 10
  попыток в минуту): перебор кода — единственный путь к чужим данным в этой схеме.

Хранилище кодов генератор не порождает: он не знает, что в проекте является участником. Проект
реализует `INsgCodeIdentityStore` и регистрирует его в контейнере.

> Требуется вызов `app.UseRateLimiter()` в `Program.cs`. В новых проектах он попадает в порождаемый
> файл; в существующих `Program.cs` не перезаписывается (он одноразовый), и строку нужно добавить
> руками.

## Проверка результата

Тестовый проект порождается заготовкой и содержит два вида проверок: smoke (приложение поднимается,
маршруты отвечают) и round-trip обмена (объект сериализуется и разбирается обратно без потерь).

Тесты самого генератора — `test/netcore_emit_test.dart`; запуск: `dart test`.

## Версия схемы и миграции

Порождается `Configurations/NsgDatabaseMigrator.cs` (перезаписывается при каждой генерации).
Механизм разделён надвое, потому что риск у половин разный.

**Сверка версии схемы при запуске — обязательна, выключателя не имеет.** Перед началом
обслуживания сервер читает журнал миграций и сравнивает с миграциями, вкомпилированными в
сборку. Если схема отстаёт — запросы не обслуживаются вовсе, в сообщении перечислены
недостающие миграции.

Защита нужна не ради удобства. Сервер на отставшей схеме не падает: EF отображает только
известные ему колонки, запись проходит, клиент получает 200, а данные ложатся неполными.
Запуск — единственный момент, когда это ещё можно заметить.

**Применение миграций — по флагу `Database:MigrateOnStartup`, по умолчанию выключено.**
Доводы против применения по умолчанию: учётная запись приложения получает права на изменение
схемы постоянно; миграция, упавшая на середине, оставляет схему в половинном состоянии;
разрушающая миграция применяется к настоящим данным молча.

Флаг стоит включать там, где один экземпляр сервера и нет отдельного администратора базы;
оставлять выключенным — на боевых хостах, где миграция должна быть осознанным шагом.

**Режим `--migrate`** — применить миграции и завершиться, не начиная обслуживание. Работает
из опубликованного бинарника, .NET SDK на сервере не нужен. Полезен именно при выключенном
флаге.

Отсутствующая база отличается от отставшей схемы и обрабатывается отдельно: журнала миграций
ещё нет, читать его нельзя, иначе вместо внятного сообщения приходит ошибка драйвера.

`EnsureCreated` не порождается намеренно: он строит схему из модели без журнала миграций, и
обновить такую базу потом можно только пересозданием с потерей данных.

### Что от этого требуется проекту

* **История миграций должна быть под контролем версий.** Это единственный артефакт в выводе
  генератора, который не восстанавливается из конфигурации: он кодирует не текущий вид схемы,
  а последовательность её состояний и переносы данных. Если каталог вывода целиком исключён
  из репозитория, для `Migrations/` нужно исключение из исключения.
* **Создание миграции остаётся шагом разработчика.** `dotnet ef migrations add` после правки
  конфигурации выполняется на машине с SDK. Описанный механизм только применяет уже созданные.
* **`Program.cs` одноразовый.** В новых проектах вызовы попадают из шаблона; в существующие
  добавляются вручную, сразу после `builder.Build()` и до `MapControllers`:

  ```csharp
  if (await NsgDatabaseMigrator.RunMigrateCommandAsync(app.Services, args)) return;
  await NsgDatabaseMigrator.EnsureSchemaCurrentAsync(app.Services, builder.Configuration);
  ```

### Проверено на PostgreSQL (21.08.2026)

| случай | ожидалось | получено |
|---|---|---|
| схема отстаёт, применение выключено | отказ обслуживать, перечень миграций | отказ, миграция названа |
| `--migrate` при отставшей схеме | применить и выйти | применил, 15 таблиц, код возврата 0 |
| `--migrate` при актуальной схеме | ничего не делать | «применять нечего» |
| схема актуальна | обслуживание идёт | выдача кода 200 |
| схема отстаёт, применение включено | домигрировать и обслуживать | домигрировал, выдача кода 200 |

## Ограничение частоты обмена кода

Окно разделяется по адресу отправителя (`RateLimitPartition` по
`RemoteIpAddress`), предел берётся из `NsgCodeAuth:ExchangeAttemptsPerMinute`,
отказ — 429.

Неразделённое окно — это не более слабая защита, а другая по смыслу вещь:
предел один на всех, и любой клиент исчерпывает его для остальных. Проверено
с двух адресов обратной петли: до правки запрос с чистого адреса получал 429
после чужих десяти попыток, после правки — своё окно.

Умолчание предела — 60 в минуту, и оно намеренно выше прежней десятки.
Барьером против перебора служит энтропия кода (не менее 40 бит), а не
ограничитель; учебная аудитория целиком выходит в сеть с одного адреса NAT, и
низкий предел отсекал бы не перебор, а группу студентов, подключающихся
одновременно.

## Проверка на настоящей базе (21.08.2026)

Эмит прогнан целиком на PostgreSQL 17 в докере: конфигурация из 14 типов модели
данных платформы эргономики, `dotnet ef migrations add Initial` + `database update`
создали 14 таблиц и 18 внешних ключей, включая ссылку таблицы `trials` на себя.

Проверено запросами, а не чтением кода:

| что проверялось | ожидалось | получено |
|---|---|---|
| выдача кода без реализации хранилища | внятный отказ | 500 с именем нереализованного `INsgCodeIdentityStore` |
| обмен верного кода | 200 | 200 |
| обмен неверного кода | 401 | 401 |
| обмен сверх предела за минуту | 429 | было 503 — **исправлено** |
| обмен с другого адреса после чужого перебора | своё окно | было общее окно — **исправлено** |
| запись с токеном анонимного входа | 200 | было 403 — **исправлено** |
| `insert-only`: тот же id, другое содержимое | 409 `content_mismatch` | 409, содержимое не перезаписано |
| `insert-only`: дословный повтор | 200 | 200 |
| удаление у типа с `allowDelete: false` | метода нет | 404 |
| кириллица в значениях полей | доходит без искажения | доходит |

Два дефекта из этого списка не проявлялись ни в `dart analyze`, ни в `dart test`,
ни при сборке порождённого сервера: и 503 вместо 429, и токен без ролей — это
рабочее поведение, отличие от договорённости видно только по ответу живого сервера.

Границы эмита, подтверждённые прогоном: `INsgCodeIdentityStore` реализуется
проектом (генератор не знает, в какой таблице лежат участники), запуск в
`Production` намеренно отклоняется до замены `Jwt:Secret` и заглушки входа по
телефону.
