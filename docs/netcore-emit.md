# Эмит netcore: что порождается

Режим включается ключом `serverEmitKind: "netcore"`. Реализация — `bin/nsgGenNetcore.dart`
(около 3000 строк). Результат — **самостоятельный сервер ASP.NET Core**, не зависящий от
`NsgServerClasses` и windows-приложения метаданных: PostgreSQL через EF Core, обмен по прежнему
wire-формату `nsg_data`.

## Состав вывода

Каталог задаётся ключом `netcoreOutputPath`.

| каталог / файл | что внутри |
|---|---|
| `Models/<Type>.cs` | сущности EF Core по описанию типа |
| `Configurations/<Type>Configuration.cs` | отображение сущности на таблицу и колонки (`pgTableName`, `pgColumnName`) |
| `Configurations/<Type>FieldMap.cs` | соответствие «поле обмена ↔ свойство C#»; wire-имя это `databaseName`, а не имя колонки |
| `Configurations/NsgTypeNameMap.cs` | соответствие имён типов обмена типам C# |
| `Configurations/NsgTypeFieldMapRegistry.cs` | реестр `FieldMap` по runtime-типу — нужен сериализатору |
| `Configurations/NsgGeneratedServicesExtensions.cs` | регистрация служб в контейнере |
| `Configurations/NsgDatabaseMigrator.cs` | сверка версии схемы при запуске и применение миграций (см. ниже) |
| `Configurations/NsgTableParts.cs` | реестр табличных частей, чтение и запись строк внутри владельца (см. ниже) |
| `Configurations/NsgFunctionArgs.cs` | разбор аргументов и упаковка результата функций; только если функции есть (см. ниже) |
| `Controllers/<Ctrl>FunctionsController.cs` | функции контроллера (`functions`): маршруты и разбор параметров (перезаписывается) |
| `Controllers/<Ctrl>FunctionsController.Custom.cs` | обработчики функций (**не перезаписывается**) |
| `Auth/NsgAuth*.cs`, `Controllers/NsgAuthController.cs` | вход по логину при `loginAuth` (см. ниже) |
| `Configurations/NsgFileStore.cs` | файлы в MinIO и выдача `GetStream` (если функция есть) |
| `Controllers/<Type>Controller.cs` | порождаемый контроллер (перезаписывается) |
| `Controllers/<Type>Controller.Custom.cs` | заготовка для своей логики (**не перезаписывается**) |
| `Wire/…` | трансляция запросов и сериализация (см. [wire-and-schema.md](wire-and-schema.md)) |
| `Auth/…` | JWT: `NsgLoginDto`, `NsgJwtOptions`, `IJwtTokenService`, `JwtTokenService`, обработчик сырого токена |
| `AppDbContext.Designer.cs` · `AppDbContext.cs` | контекст: порождаемая часть и ручная |
| `<Namespace>.csproj`, `Program.cs`, `appsettings.json`, `launchSettings.json` | размещение приложения |
| `<Namespace>.Tests/` | заготовка тестового проекта: smoke и round-trip обмена |
| `Enums/…` | перечисления |

## Что перезаписывается, а что нет

Разделение проведено намеренно и опирается на `_writeOneShot`: файл пишется, **только если его ещё
нет** (либо при `forceOverwrite`).

**Перезаписывается при каждой генерации:** модели, перечисления, конфигурации, `FieldMap`, реестры,
порождаемая часть контроллера, контроллер входа по коду, `AppDbContext.Designer.cs`,
`NsgDatabaseMigrator.cs`, `UserRoles.cs`.

**Wire-слой одноразовый**, вопреки прежней записи в этом документе: файлы `Wire/` пишутся только
если их ещё нет. Практическое следствие — исправления генератора в wire не доходят до проектов, где
он уже создан; пересмотр требует отдельного решения.

**Пишется один раз и далее не трогается:** `*.Controller.Custom.cs`, ручная часть `AppDbContext.cs`,
`csproj`, `Program.cs`, `appsettings.json`, `launchSettings.json`, файлы тестового проекта, файлы
аутентификации.

Практическое следствие: **своя логика живёт в `.Custom.cs`**, и перегенерация её не затирает. Правка
порождаемого файла будет потеряна при следующем запуске.

## Порождаемые операции контроллера

Состав определяется флагами метода (`allowGetter`, `allowCreate`, `allowPost`, `allowDelete` —
см. [config-reference.md](config-reference.md)).

| операция | маршрут | поведение |
|---|---|---|
| чтение | `POST Api/<Type>` | тело — параметры запроса `nsg_data`: фильтр `NsgCompare`, сортировка, `ReadReferences`, `Top` |
| запись | `POST Api/<Type>/Post` | принимает **массив** объектов; для каждого — поиск по первичному ключу: найден → обновление, не найден → вставка |
| удаление | `POST Api/<Type>/Delete` | массив идентификаторов |

Точки расширения в `.Custom.cs`: `CustomizeReadQuery`, `OnBeforeSave`, `OnBeforeDelete`.

### Режим записи

По умолчанию `Post` выполняет upsert: найденный по идентификатору объект обновляется присланным
содержимым. Для типов, которые пишутся один раз и не изменяются, задаётся `postMode: "insert-only"`
(см. [config-reference.md](config-reference.md)): совпадающее содержимое принимается как повтор,
отличающееся отклоняется с `409`.

Сравнение выполняет порождаемый `Wire/NsgWireComparer.cs` — по объектам обмена, а не по сущностям.
Перед отказом вызывается частичный метод `OnPostConflict(incoming, existing)`, в котором проект может
записать расхождение в свой журнал; заготовка объявлена в `.Custom.cs`.

## Табличные части

Табличная часть — поле `List<Row>` владельца, где `Row` — строка (`databaseType` оканчивается на
`.Строка` или `isTableRow: true`). В базе это отдельная таблица со ссылкой на владельца и каскадным
удалением; в обмене — **массив строк внутри объекта владельца**, как их шлёт и ждёт `nsg_data`.

Логика лежит в перезаписываемом `Configurations/NsgTableParts.cs`, а не в `Wire/`: слой `Wire/`
одноразовый, и правка в нём не дошла бы до созданных проектов. Контроллер владельца порождается с
вызовами `NsgTableParts`; у типов без табличных частей контроллер прежний.

**Чтение.** Часть попадает в ответ, если её имя есть в `ReadReferences` — клиент по умолчанию
просит все части. Путь через часть (`files.authorId`) сводится к самой части: строки едут внутри
объекта, а их ссылки клиент дочитывает отдельными запросами. Прежде такой путь падал в
`DotPathResolver` с `NotImplementedException`. Строки отдаются в порядке, в котором были присланы.

**Запись** повторяет `NsgServerMetadataItem.ServerToNsgField` прежнего сервера:

| случай | поведение |
|---|---|
| ключа части нет в присланном объекте | часть не трогается |
| `newTableLogic` не задан (по умолчанию в `nsg_data`) | присланный массив — полный состав: неприсланные строки удаляются, порядок берётся из массива |
| `newTableLogic: true` | строки с `docState = 2` удаляются, неприсланные остаются на месте, новые встают в конец; если прислана вся часть — порядок из массива |
| идентификатор строки повторяется в массиве | `400`, ничего не записано |
| негодный идентификатор или значение в строке | `400` с именем части и поля |
| идентификатор строки занят строкой другого владельца (копия объекта) | строке выдаётся новый идентификатор |
| строка без идентификатора | выдаётся новый |

Ссылка строки на владельца проставляется сервером, присланное `ownerId` не учитывается. Ответ на
запись содержит все части: клиент заменяет объект ответом, и без строк часть на экране опустела бы.

**Порядок строк.** У строки табличной части порождается служебное свойство `RowNumber` (колонка
`row_number`). В обмен оно не входит — порядок передаётся порядком массива. Поле описания с именем
`RowNumber` или колонкой `row_number` в строке отклоняется при генерации.

> Проекту, где строки табличных частей уже есть в схеме (например, `BannerPlayerListTable`
> в `futbolista_server`), после перегенерации нужна миграция: добавляется колонка `row_number`.

### Проверено на PostgreSQL 16 (17.11.2026)

Порождённый сервер (задача с двумя табличными частями), миграция EF, запросы в формате `nsg_data`:

| случай | получено |
|---|---|
| новая задача с тремя строками | строки в ответе на запись, в присланном порядке, с клиентскими id и `ownerId` владельца; `RowNumber` в обмен не уходит |
| чтение с `ReadReferences: [checkList, files, files.authorId]` | строки внутри объекта, запрос не падает |
| чтение без запроса части | ключа части в ответе нет |
| полный массив без `newTableLogic` | неприсланная строка удалена, порядок как прислан, правка строки сохранена |
| объект без ключа части | строки на месте |
| `newTableLogic`, строка с `docState = 2` и новая строка | помеченная удалена, неприсланная осталась, новая в конце |
| повтор id строки · негодный id строки | `400`, данные не изменились |
| копия объекта с занятыми id строк | у копии новые id, строки оригинала не тронуты |
| удаление владельцев | строки удалены каскадом (в таблицах строк 0 записей) |

## Функции контроллера

Функции (`functions` контроллера в `generation_config.json`, описание то же, что у классического эмита) порождаются в
отдельном классе `<Ctrl>FunctionsController` (`DataController` → `DataFunctionsController`) с тем же
префиксом маршрута, что у типов: `POST Data/<apiPrefix функции>`; при `apiType: "get, post"`
добавляется `GET`. Совпадение маршрута функции с маршрутом типа того же контроллера — отказ генерации.

Порождаемое действие читает аргументы и вызывает обработчик `On<Name>(args, <параметры>)` —
`private partial` метод с результатом. Его тело живёт в одноразовом `.Custom.cs`; первый прогон
пишет заготовки с `NotImplementedException`. Функция, добавленная после первого прогона, в заготовку
сама не попадёт: сборка откажет «partial method must have an implementation», и обработчик
дописывается по объявлению из порождаемой половины.

**Параметры** ищутся в `Parameters` тела (так их шлёт `nsg_data`), затем в строке адреса (ссылки на
файлы и картинки приходят без тела). Через `args.Request` обработчику доступен весь запрос
(`Compare`, `ReadReferences`, `Top`).

| тип параметра | C# | откуда |
|---|---|---|
| `String`, `int`, `double`, `bool`, `DateTime`, `Guid` | одноимённый | строка или JSON-литерал |
| `Enum<X>` | `X` | число |
| `Reference<X>` | `X` | объект в формате обмена (`toJson` клиента) |
| `List<простой>`, `List<X>` | `List<…>` | массив |

Отсутствующий или негодный параметр — `400 wire_format` с именем параметра (и индексом элемента
списка). Прежний сервер подставлял вместо негодной даты «сейчас» и падал `500` на отсутствующем
параметре; здесь вызов не выполняется.

**Результат** упаковывается так, как его ждёт клиент:

| тип результата | обработчик возвращает | ответ |
|---|---|---|
| простой, `Enum<X>` | значение | `{"results": [значение]}` — `NsgSimpleRequest`; дата — ISO UTC, перечисление — число |
| `List<простой>`, `List<Enum>` | `IEnumerable<…>` | `{"results": [...]}` |
| `Reference<X>` | `X?` | массив из одного объекта или пустой — как ответ чтения |
| `List<X>` | `IEnumerable<X>` | массив объектов; табличные части в ответ не входят |
| `Binary`, `Image` | `IActionResult` | как вернул обработчик (`File(...)`) |

Уровень доступа (`authorize`) переводится так же, как у типов: `user`/`admin` — роль, `anonymous` —
любой вошедший, `none` — без атрибута.

Проверено 17.11.2026 на PostgreSQL 16 (WSL) образцом с десятью функциями всех видов:

| сценарий | результат |
|---|---|
| все простые типы, перечисление, `Top` из запроса | разобраны; числа и `bool` принимаются и строкой, и литералом |
| нет параметра · негодные число, дата, Guid · дробь в `int` · тело не JSON | `400` с именем параметра |
| параметр с именем `params` | экранирован `@params`, работает |
| `DateTime` результатом | `"2026-11-17T10:30:00Z"` в `results` |
| `Reference` есть / нет · `List<Reference>` | массив объектов / пустой массив |
| `List<int>` параметром, негодный элемент | сумма верна; `400` с индексом |
| объект параметром (запись в БД), негодное поле объекта | записан и читается; `400` с именем параметра и поля |
| `Binary` по `GET` с параметром в адресе и по `POST` | файл отдан; без параметра — `400` |
| `authorize: user` без токена · функция только `POST` по `GET` | `401` · `405` |
| чтение типа рядом с функциями, сценарий табличных частей | без изменений (20 из 20) |

## Вход по логину (`loginAuth`)

Включается ключом `loginAuth: true`. Повторяет контракт `Api/Auth/*`, которым пользуются `nsg_data`
и `nsg_login` (телефон или почта, код подтверждения, пароль), но хранит учётные записи, сессии и
коды в базе, а не в памяти процесса: при двух экземплярах сервера на одной базе код, отправленный
одним, проверяется другим, а выход и смена пароля действуют сразу везде.

| файл | вид | содержимое |
|---|---|---|
| `Auth/NsgAuthModels.cs` | перезапись | таблицы `nsg_auth_users`, `nsg_auth_sessions`, `nsg_auth_codes` |
| `Auth/NsgAuthService.cs` | перезапись | токены, сессии, коды, пароли (PBKDF2-SHA256, 100 000 итераций) |
| `Auth/NsgAuthTokenHandler.cs` | перезапись | проверка токена по сессии; приставка `Bearer ` допускается |
| `Auth/NsgCodeDispatcher.cs` | перезапись | отправка кода: почта (SMTP), SMS (HTTP-шлюз) |
| `Controllers/NsgAuthController.cs` | перезапись | `Api/Auth/*` |
| `Auth/NsgAuthHooks.cs` | **один раз** | `OnLoggedInAsync(user, isNewUser)` — здесь проект заводит свой профиль пользователя |

Таблицы входа попадают в `AppDbContext`; миграцию проект создаёт как обычно
(`dotnet ef migrations add …`).

| точка | поведение |
|---|---|
| `GET AnonymousLogin` | анонимный токен (роль `anonymous`, без записи в базе) |
| `GET CheckToken` | токен действующей сессии — тот же токен; иначе `isError`, `errorCode: 401` (HTTP 200) |
| `POST PhoneLoginRequestSMS` (`…Email`) | `register: false` — вход по паролю; `register: true` — отправка кода, привязанного к токену запроса |
| `POST PhoneLogin` | код → вход; при `register` и `newPassword` — новый пароль и закрытие прежних сессий |
| `GET Logout` | отзыв своей сессии |
| `GET CheckVersion`, `SetLocale` | заглушки «всё в порядке» |

Защита:

- вход выполняется на адрес, **куда ушёл код**, а не на присланный при вводе: иначе код, полученный
  на свой телефон, открывал бы чужую учётную запись;
- код хранится хешем, одноразовый, срок жизни `CodeLifetimeSeconds` (600), попыток `MaxAttempts` (3),
  повторная отправка не раньше `SmsResendSeconds`/`EmailResendSeconds`;
- запросы входа и кода ограничены по адресу (`LoginAttemptsPerMinute`, 429);
- анонимный токен там, где нужен пользователь, получает 401 (как прежде), а не 403;
- отладочного входа в коде нет. Вход с постоянным кодом для проверки в магазинах приложений
  задаётся только списком `Auth:ReviewLogins` (по умолчанию пуст);
- вне Development без настроенного канала (`Auth:Smtp` или `Auth:Sms`) сервер не запускается;
  в Development код без канала пишется в журнал;
- запрет заглушки `0000` в Production при `loginAuth` не нужен и не порождается; пилотный
  `AuthController` (при типе `UserItem`) тоже.

Совместимость ответа: `secondsRemaining` и `secondsBeforeRepeat` пишутся с дробной частью
(`600.0`) — клиент читает их `as double`, и целое `600` роняет разбор на мобильной платформе.
Ответ на запрос кода несёт `isAnonymous: false`, как прежний сервер (у него поле опускалось).

Кто сделал запрос — `User.NsgUserId()` (учётная запись входа) и `User.NsgSessionId()`.

Проверено 17.11.2026 на PostgreSQL 16 (WSL), 38 из 38: анонимный токен и отказ ему в функциях
пользователя (401), запрос кода и нормализация телефона и почты, повтор раньше срока (40300),
неверный код (40300), исчерпание попыток (40301) и одноразовость кода (40303), подмена номера при
вводе кода (вход на адрес кода), вход по паролю и неверный пароль (40104), выход одной сессии без
влияния на другую, смена пароля с закрытием прежних сессий, постоянный код из `ReviewLogins` без
отправки, `Bearer`-приставка, подделанный токен (401), ограничение частоты (429).

## Файлы (MinIO)

Функция контроллера с именем `GetStream` и типом `Binary`/`Image` обслуживается сервером сам —
своего обработчика у неё нет. Файлы лежат в MinIO, как в futbolista (тот же клиент `Minio` 7.0.0).

- Объект хранит **ключ** файла (`attachments/…/<guid>.pdf`), не адрес. Записывает бизнес-логика
  через `NsgFileStore.SaveAsync(bytes, folder, ext)` — имя файла всегда случайное.
- `GetStream?path=<ключ>` отвечает `302` на подписанную ссылку со сроком `Files:UrlLifetimeMinutes`
  (60): файл идёт клиенту из MinIO напрямую. Клиент менять не нужно — он и так строит
  `{server}/Data/GetStream?path=…`, а `Image.network` и загрузчики следуют перенаправлению.
- Ключ проверяется: `..`, `.`, абсолютный путь, диск, схема, `?`/`#` — `404` без обращения к
  хранилищу; всё прочее — только внутри `Files:Prefix` своего бакета.

Прежний `GetStream` (NsgServerFileSharing) отдавал **любой файл с диска сервера** без токена:
`..` и абсолютные пути не отвергались, а абсолютный путь ещё и отменял каталог файлов.

`GetStream` по-прежнему без токена: картинки грузятся без заголовков. Доступ к файлу — знание
случайного ключа и короткоживущая ссылка. Подписанная ссылка действительна только для адреса
`Files:Endpoint` — клиент должен видеть MinIO по тому же адресу.

Вне Development без `Files:Endpoint`, `Bucket`, `AccessKey`, `SecretKey` сервер не запускается.

`Files:Endpoint` принимает `host:port` или `https://host:port`; схема в адресе задаёт `UseSsl`.
Так адрес переносится из Infisical (`MinioEndpoint`) без правки.

Проверено 17.11.2026 на MinIO ноды 133 (бакет `tasktuner`, ключи из Infisical через `secrets-pull.ps1` nsg-infra, префикс `ttsample-check`): запись, 302 на подписанную ссылку внутри префикса, сам файл по ссылке, отказ 404 без перенаправления на 8 видов недопустимых ключей, 404 от MinIO на отсутствующий файл, удаление — 17 из 17. ## Вход по одноразовому коду

Включается ключом `anonymousCodeAuth: true`. Предназначен сценариям, где у участника нет и не должно
быть учётной записи: опросы, тестирования, учебные работы с анонимной моделью данных.

Код выдаётся сервером при подключении и служит **единственным** ключом доступа к собственным данным.
Порождаются четыре составляющие:

| файл | назначение |
|---|---|
| `Auth/NsgAccessCode.cs` | выдача кода, хеширование, сверка за постоянное время |
| `Auth/NsgCodeAuthOptions.cs` | длина кода, общий секрет, предел попыток обмена |
| `Auth/INsgCodeIdentityStore.cs` | **точка расширения проекта**: как хранятся коды и что считается участником |
| `Controllers/NsgCodeAuthController.cs` | `Issue` — выдать код новому участнику, `Exchange` — обменять код на токен |

Заложенные решения и их причины:

* **Код случаен и длинен.** Алфавит из 32 знаков без визуально неразличимых (`0/O`, `1/I/L`), по
  умолчанию 10 знаков — ровно 50 бит энтропии. Длина короче 8 знаков отклоняется: меньше 40 бит
  подбирается.
* **Хранится хеш, а не код.** Утечка хранилища не открывает доступ к данным. Соль на запись
  невозможна — поиск идёт по хешу; её отсутствие безопасно именно потому, что код случаен: словарной
  атаки, от которой защищает соль, здесь не существует. Общий секрет (`Pepper`) задаётся конфигурацией
  развёртывания.
* **Сверка за постоянное время** (`FixedTimeEquals`): время ответа не должно зависеть от числа
  совпавших знаков.
* **Ответ на неизвестный код неотличим от ответа на ошибочный.** Иначе по различию ответов можно было
  бы отделять существующие коды от несуществующих.
* **Ограничение частоты обмена** регистрируется автоматически (`nsg-code-exchange`, по умолчанию 10
  попыток в минуту): перебор кода — единственный путь к чужим данным в этой схеме.

Хранилище кодов генератор не порождает: он не знает, что в проекте является участником. Проект
реализует `INsgCodeIdentityStore` и регистрирует его в контейнере.

> Требуется вызов `app.UseRateLimiter()` в `Program.cs`. В новых проектах он попадает в порождаемый
> файл; в существующих `Program.cs` не перезаписывается (он одноразовый), и строку нужно добавить
> руками.

## Что требуется порождённому клиенту

Dart-эмит (`doDart`) порождает модели и контроллер поверх `nsg_data`. Собирающийся клиент требует в
`pubspec.yaml` трёх прямых зависимостей, и две из них неочевидны:

| зависимость | почему прямая |
|---|---|
| `nsg_data` | модели и слой обмена |
| `get` | порождённый контроллер наследует `NsgBaseController`, а тот — `GetxController`; пакет импортируется прямо в порождённом коде, и опора на транзитивную зависимость ломается при её смене |
| `package_info_plus` | версия приложения читается в `onInit` порождённого контроллера |

Версия `get` должна совпадать по мажору с той, на которой стоит `nsg_data`: контроллеры наследуют его
классы, и расхождение мажора не разрешается вовсе.

**`emitSchemaHash` требует `nsg_data` не старее 22.08.2026** — см. справочник конфигурации. При более
ранней библиотеке порождённый клиент не собирается.

## Версия схемы и миграции

Порождается `Configurations/NsgDatabaseMigrator.cs` (перезаписывается при каждой генерации).
Механизм разделён надвое, потому что риск у половин разный.

**Сверка версии схемы при запуске — обязательна, выключателя не имеет.** Перед началом
обслуживания сервер читает журнал миграций и сравнивает с миграциями, вкомпилированными в
сборку. Если схема отстаёт — запросы не обслуживаются вовсе, в сообщении перечислены
недостающие миграции.

Защита нужна не ради удобства. Сервер на отставшей схеме не падает: EF отображает только
известные ему колонки, запись проходит, клиент получает 200, а данные ложатся неполными.
Запуск — единственный момент, когда это ещё можно заметить.

**Применение миграций — по флагу `Database:MigrateOnStartup`, по умолчанию выключено.**
Доводы против применения по умолчанию: учётная запись приложения получает права на изменение
схемы постоянно; миграция, упавшая на середине, оставляет схему в половинном состоянии;
разрушающая миграция применяется к настоящим данным молча.

Флаг стоит включать там, где один экземпляр сервера и нет отдельного администратора базы;
оставлять выключенным — на боевых хостах, где миграция должна быть осознанным шагом.

**Режим `--migrate`** — применить миграции и завершиться, не начиная обслуживание. Работает
из опубликованного бинарника, .NET SDK на сервере не нужен. Полезен именно при выключенном
флаге.

Отсутствующая база отличается от отставшей схемы и обрабатывается отдельно: журнала миграций
ещё нет, читать его нельзя, иначе вместо внятного сообщения приходит ошибка драйвера.

`EnsureCreated` не порождается намеренно: он строит схему из модели без журнала миграций, и
обновить такую базу потом можно только пересозданием с потерей данных.

### Что от этого требуется проекту

* **История миграций должна быть под контролем версий.** Это единственный артефакт в выводе
  генератора, который не восстанавливается из конфигурации: он кодирует не текущий вид схемы,
  а последовательность её состояний и переносы данных. Если каталог вывода целиком исключён
  из репозитория, для `Migrations/` нужно исключение из исключения.
* **Создание миграции остаётся шагом разработчика.** `dotnet ef migrations add` после правки
  конфигурации выполняется на машине с SDK. Описанный механизм только применяет уже созданные.
* **`Program.cs` одноразовый.** В новых проектах вызовы попадают из шаблона; в существующие
  добавляются вручную, сразу после `builder.Build()` и до `MapControllers`:

  ```csharp
  if (await NsgDatabaseMigrator.RunMigrateCommandAsync(app.Services, args)) return;
  await NsgDatabaseMigrator.EnsureSchemaCurrentAsync(app.Services, builder.Configuration);
  ```

## Ограничение частоты обмена кода

Окно разделяется по адресу отправителя (`RateLimitPartition` по
`RemoteIpAddress`), предел берётся из `NsgCodeAuth:ExchangeAttemptsPerMinute`,
отказ — 429.

Неразделённое окно — это не более слабая защита, а другая по смыслу вещь:
предел один на всех, и любой клиент исчерпывает его для остальных. Проверено
с двух адресов обратной петли: до правки запрос с чистого адреса получал 429
после чужих десяти попыток, после правки — своё окно.

Умолчание предела — 60 в минуту, и оно намеренно выше прежней десятки.
Барьером против перебора служит энтропия кода (не менее 40 бит), а не
ограничитель; учебная аудитория целиком выходит в сеть с одного адреса NAT, и
низкий предел отсекал бы не перебор, а группу студентов, подключающихся
одновременно.

Эмит прогнан целиком на PostgreSQL 17 в докере: конфигурация из 14 типов модели
данных платформы эргономики, `dotnet ef migrations add Initial` + `database update`

| обмен неверного кода | 401 | 401 |
| обмен сверх предела за минуту | 429 | было 503 — **исправлено** |
