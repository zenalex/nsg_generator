# Справочник конфигурации

Все ключи ниже действительно разбираются генератором — список сверен с `parsedJson['…']` в
`bin/nsgGenerator.dart`, `bin/nsgGenDataItem.dart`, `bin/nsgGenDataItemField.dart`,
`bin/nsgGenMethod.dart`. Ключ, отсутствующий здесь, генератором игнорируется молча.

## 1. `generation_config.json` — корень

| ключ | назначение |
|---|---|
| `serverEmitKind` | `netcore` — самостоятельный сервер ASP.NET Core; отсутствует или иное — классический эмит на `NsgServerClasses` |
| `targetFramework` | `net5.0`…`net10.0`; при пустом значении подставляется `net5.0` |
| `cSharpNamespace` | пространство имён серверного проекта (обязателен при `doCSharp`) |
| `cSharpPath` | каталог вывода серверного проекта (классический эмит) |
| `netcoreOutputPath` | каталог вывода при `serverEmitKind: netcore` |
| `dartPath` | каталог вывода Dart-моделей клиента |
| `doCSharp` · `doDart` | включение серверной и клиентской генерации |
| `applicationName` | имя приложения, попадает в клиентский `NsgDataProvider` |
| `controller` | описание контроллера клиента: список методов (см. раздел 3) |
| `enums` | список перечислений |
| `useLocalization` | генерация локализуемых представлений |
| `defaultLocale` | локаль по умолчанию |
| `newTableLogic` | новая логика табличных частей на клиенте |
| `useStaticDatabaseNames` | статические имена полей БД |
| `supportChat` | генерация интеграции чата поддержки |
| **`anonymousCodeAuth`** | вход участника по одноразовому непредсказуемому коду вместо учётной записи (см. [netcore-emit.md](netcore-emit.md)) |
| **`emitSchemaHash`** | передавать ли хеш схемы в `NsgDataProvider(schemaHash:)`; требует `nsg_data` с поддержкой параметра, умолчание — `false` (см. ниже) |
| **`netcoreGeneratedSubdir`** | подкаталог для перезаписываемых файлов netcore-эмита; пусто — прежнее поведение, всё в один каталог (см. ниже) |

### Ключ `netcoreGeneratedSubdir`

Разводит вывод netcore-эмита на две группы: перезаписываемое уходит в
`<netcoreOutputPath>/<значение>`, одноразовое остаётся в корне проекта.

| остаётся в корне (одноразовое) | уходит в подкаталог (перезаписывается) |
|---|---|
| `<Namespace>.csproj`, `Program.cs`, `appsettings.json`, `Properties/launchSettings.json` | `Models/`, `Enums/` |
| `Controllers/<T>Controller.Custom.cs`, `Controllers/AuthController.cs` | `Controllers/<T>Controller.cs`, `Controllers/NsgCodeAuthController.cs` |
| `Auth/` целиком | `Configurations/` целиком |
| `Wire/` целиком | `AppDbContext.Designer.cs` |
| ручная часть `AppDbContext.cs` | |

Смысл не в порядке ради порядка. Пока обе группы лежат вместе, отличить порождаемое от написанного
руками можно только по документации — а хранить в репозитории нужно ровно вторую группу. Правило
хранения при разделении становится однострочным: подкаталог целиком не хранится.

> **Оговорка о wire-слое.** Он одноразовый, то есть исправления генератора в нём **не доходят** до
> проектов, где он уже создан. Документация раньше утверждала обратное; утверждение исправлено по
> факту кода. Пересмотр этой классификации — отдельное решение: сделать wire перезаписываемым значит
> затирать возможные правки в существующих проектах.

### Ключ `emitSchemaHash`

Хеш схемы конфигурации порождается всегда — в `_schema_meta.dart` рядом с моделями. Ключ управляет
только тем, передаётся ли он клиентским контроллером в `NsgDataProvider`.

Умолчание `false` выбрано не из осторожности, а по факту: параметр `schemaHash` появился в `nsg_data`
только 22.08.2026, и порождённый клиент против более ранней библиотеки **не собирается** — параметра
у провайдера нет. Обнаруживается это не здесь: генератор отрабатывает, его тесты проходят, а ошибка
приходит от анализатора чужого проекта при первой сборке настоящего клиента.

Включать имеет смысл, когда клиент собирается против `nsg_data` не старее указанной даты. Тогда
запросы получают заголовок `X-Nsg-Schema-Hash`; сервер использует его информационно — для журналов и
телеметрии, а не для отклонения запросов. Совместимость обмена обеспечивается толерантным чтением, а
не сверкой хешей.

| `useLocalization` · `useStaticDatabaseNames` | переопределение корневых настроек |

## 3. Метод контроллера (элемент `controller.methods`)

Здесь задаётся **состав операций**: генератор порождает только то, что разрешено.

| ключ | назначение |
|---|---|
| `name` | имя метода и основа маршрута |
| `dataTypeFile` · `dataType` | описание типа данных метода |
| `apiPrefix` | префикс маршрута |
| `getterType` · `type` | HTTP-метод чтения (по умолчанию `POST`) |
| **`allowGetter`** | порождать чтение (по умолчанию — да) |
| **`allowCreate`** | порождать создание объекта |
| **`allowPost`** | порождать запись (`Post`) |
| **`allowDelete`** | порождать удаление (`Delete`) |
| **`postMode`** | режим записи: `upsert` (по умолчанию) или `insert-only` (см. ниже). Неизвестное значение — ошибка генерации |
| `authorize` | уровень доступа ко всем операциям метода |
| `authorize.get` · `authorize.create` · `authorize.post` · `authorize.delete` | уровень доступа по каждой операции отдельно |
| `description` | описание |

**Отсутствие операции и запрет операции — разные вещи.** При `allowDelete: false` метод удаления в
порождённом контроллере **не появляется вовсе**; при `authorize.delete` он существует, но требует
прав. Для данных, которые не должны удаляться никогда (журналы, измерения, аудит), правильным
является первое.

## 4. Поле типа (элемент `fields`)

| ключ | назначение |
|---|---|
| `name` | имя поля |
| `type` | тип значения |
| `databaseName` | имя поля в обмене и в БД классического эмита |
| `pgColumnName` | имя колонки PostgreSQL (netcore-эмит) |
| `isPrimary` | первичный ключ |
| `maxLength` | предельная длина |
| **`allowPost`** | клиенту разрешено присылать это поле (по умолчанию — да) |
| `writeOnClient` · `writeOnServer` | сторона, изменяющая поле |
| `referenceName` · `referenceType` · `referenceTypes` · `defaultReferenceType` | ссылочные поля |
| `useDate` · `useTime` | использование даты и времени |
| `userName` · `userVisibility` | пользовательское имя и видимость |
| `apiPrefix` | префикс для поля-ссылки |
| `description` | описание |

Поля с `writeOnServer: true` и `allowPost: false` исключаются из приёма: сервер их не берёт из
запроса, даже если клиент прислал.

### Режим записи `postMode`

| значение | поведение при существующем идентификаторе |
|---|---|
| `upsert` (по умолчанию) | объект обновляется присланным содержимым |
| `insert-only` | содержимое сравнивается: совпало — успех (повторная отправка идемпотентна), не совпало — `409` и вызов `OnPostConflict` |

`insert-only` предназначен типам, которые пишутся один раз и не изменяются:
измерения, события, журналы. Для них тихая перезапись уничтожает единственный
признак сбоя клиента или порчи данных при хранении.

Сравнение идёт по объектам обмена, а не по сущностям, поэтому поля, которые
клиент присылать не вправе (`allowPost: false`, `writeOnServer`), в сравнение не
попадают.

## 5. Пример: тип только для добавления

Конфигурация для данных, которые пишутся один раз и не изменяются:

```json
{
  "name": "Trial",
  "dataTypeFile": "trial.json",
  "authorize": "user",
  "allowGetter": "true",
  "allowPost": "true",
  "allowDelete": "false",
  "postMode": "insert-only"
}
```

Порождается чтение и вставка; операции удаления в контроллере не существует,
а повторная присылка объекта с изменённым содержимым отклоняется.
